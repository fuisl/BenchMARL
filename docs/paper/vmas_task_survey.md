## Vectorized, in simple terms

"Vectorized" means VMAS steps an arbitrary number of environments **in one batched PyTorch tensor op**, instead of a Python `for env in envs: env.step()` loop. Every entity's state (position, velocity, rotation, angular velocity) carries a leading batch dimension; physics (semi-implicit Euler integration, force-based collisions) is computed for the whole batch at once. This is GPU **SIMD**: the same instruction executed across the batch inside a GPU warp. Consequence: on CPU it's still faster than a loop (paper reports up to 5x vs. MPE), but on GPU the wall-clock cost is roughly *independent of batch size* — the paper measured 30,000 parallel environments in under 10s (>100x faster than MPE, which is CPU-only and scales linearly in environment count).

How this repo actually uses it: `benchmarl/environments/vmas/common.py`'s `VmasClass.get_env_fun` builds a `torchrl.envs.libs.vmas.VmasEnv(scenario=..., num_envs=N, device=...)` — `num_envs` is the batch size, `device="cuda"` puts the whole batched simulation on GPU. This is the same `num_envs` you already set via `experiment.on_policy_n_envs_per_worker` / `off_policy_n_envs_per_worker`. The original paper benchmarked through **RLlib** instead (VMAS ships an RLlib wrapper too); this repo uses **TorchRL/TensorDict** — different RL glue, same vectorized VMAS core underneath.

How the original paper's benchmarked algorithms used it: PPO-based, trained via RLlib's vectorized interface, 400 training iterations × 60,000 environment interactions/iteration, 2-layer tanh MLP actor+critic, mean±std over 10 seeds. Four models compared, spanning the centralization spectrum:
- **CPPO** — centralized actor *and* critic (whole team treated as one super-agent).
- **MAPPO** — centralized critic, decentralized (shared-parameter) actor.
- **IPPO** — decentralized critic and actor, parameters shared across agents.
- **HetIPPO** — IPPO with parameter sharing *disabled* (heterogeneous per-agent policies).
- **Heuristic** — hand-designed, scenario-specific, decentralized.

This repo's `fine_tuned/vmas/conf/config.yaml` is the equivalent "how a real experiment is scaled" recipe here: `on_policy_n_envs_per_worker: 600`, `on_policy_collected_frames_per_batch: 60_000` (matches the paper's per-iteration interaction count), `max_n_frames: 10_000_000`, `train_device`/`sampling_device`/`buffer_device: cuda`, `loggers: [wandb]`, 200 eval episodes. It leaves `algorithm`/`task` as `???` (required CLI overrides) and relies on each task's own `benchmarl/conf/task/vmas/<task>.yaml` for scenario-specific parameters — see "Config reuse" below.

## Common to all six scenarios

- **World**: holonomic 2D physics (agents don't control orientation directly), force-based collisions, semi-implicit Euler integration — same core for every task.
- **Action**: a 2D force (or, for Give Way, a velocity command through a `VelocityController`), continuous by default; BenchMARL's `VmasClass` always requests `clamp_actions=True` (bounds enforced) and supports both continuous and discrete (`categorical_actions=True`) action modes for every VMAS task.
- **Policy convention**: 2-layer MLP, tanh activation, shared parameters across agents unless the scenario specifically needs heterogeneity (Give Way).
- **`state_spec` is `None`** for every VMAS task in this repo (`VmasClass.state_spec`) — there is no privileged full-state observation; a "central"/"relational" world model has to be built by concatenating agents' own observation entries at the TensorDict level (the collector already groups all agents' observations together, even though no single agent's own observation vector contains another agent's state).

Buzz Wire is CoDreamer's description (Appendix D.7, arXiv:2406.13600v1): "a lack of synchronised movement can result in one agent pulling the other into the borders thereby causing failure" — CoDreamer's own experiments use it with **discrete** actions (5 per agent); the scenario itself defaults to continuous force, so use CoDreamer as task-selection evidence, not as an identical continuous-MPC protocol reference (per experiment_plan.md M1).

### Notes worth carrying into M1

1. **Cross-agent coupling never shows up as "observe the other agent's state/action" in any of these six tasks by default.** That's the opposite of a convenient setup for this paper's core claim (`z_{t+1}^i = f(z_t^i, a_t^i, {z_t^j, a_t^j}_{j≠i})`) — an "Independent" world model trained on the *default* per-agent observation already can't see `{z_t^j, a_t^j}`, so it isn't just "choosing to ignore" other agents, it structurally cannot. The world-model input has to be built explicitly from the batched TensorDict (concatenating agents' own observation/action entries within a group), not read off a single agent's observation. Also: Give Way ships `observe_rel_pos` as a literal on/off switch for exactly this — per experiment_plan.md M1, the independent baseline should use the **task default** (`observe_rel_pos=False`) rather than a redesigned observation, so this is not a free choice to make later, it's already answered by "keep task defaults."
2. Dropout, Transport, Wheel, and Buzz Wire already use a **shared/team reward** (identical scalar to every agent) — that simplifies the planning-cost definition (`J` is the same regardless of which agent's rollout you score) but means "does the model predict *my* reward" and "does the model predict *the team's* reward" collapse into the same question for these four tasks, not for Give Way (per-agent shaping + collision terms differ per agent) or Passage (`shared_reward` is a config toggle).
3. The exploratory coupling labels track the physics, not a validated ordering (experiment_plan.md is explicit that task names alone don't establish this): Dropout has no shared object at all (coupling is a reward artifact); Give Way and Passage share *space* (collision avoidance); Transport and Wheel share one *physical object* whose mass makes single-agent solutions physically impossible; Buzz Wire goes further with a rigid `Joint` constraint plus an episode-ending failure mode rather than a smooth penalty. Whether this ordering actually predicts a bigger relational-vs-independent gap is exactly what M1's pilots are for.
4. `Passage`'s `n_passages` (default 1) and `Give Way`'s `mirror_passage`/`observe_rel_pos` are **not** settings to permanently fix per task — experiment_plan.md M1 treats any interaction-strength change as "a separate, motivated ablation," not a default-suite requirement. Keep task defaults for the baseline comparisons; only touch these if a specific pilot result motivates it.
5. **Behaviour-policy risk, worth checking empirically before M3 collects data from any of these.** The original VMAS paper found that *all* PPO-based baselines (CPPO, MAPPO, IPPO) performed *worse than the hand-designed heuristic* on **Wheel**. On **Give Way**, it found something more specific: parameter-shared decentralized algorithms (IPPO, MAPPO — the ones this repo's README quickstart defaults to) *fail outright*, and only a centralized actor (CPPO) or explicitly heterogeneous, non-shared policies (HetIPPO, i.e. `share_policy_params=False`) solve it. **Buzz Wire** wasn't in the original paper's RL benchmark at all (CoDreamer evaluates it with discrete actions and Dreamer-style imagination, not PPO or continuous MPC), so there's no existing evidence a simple continuous-action behaviour policy solves it either. Net effect: for Give Way, M3's cooperative-policy data collection likely needs `share_policy_params: False` (or a centralized critic), not the repo's shared-parameter default; for Wheel and Buzz Wire, whether *any* straightforward continuous-action policy solves the task at all should be checked (a cheap Level-0/1 MAPPO/IPPO training run) before relying on cooperative trajectories from them.

## Config reuse (how other experiments here are already configured)

No new config pattern is needed — the existing one already separates concerns cleanly:

- **Task-specific parameters** (agent count, masses, episode length, reward toggles) live in `benchmarl/conf/task/vmas/<task>.yaml`, one per scenario, already present and populated with the VMAS package's own defaults for all six tasks above. Reuse as-is per `coding_rules.md` rule 15 — override only to answer an explicit question, not as a default suite setting (note 4 above).
- **Training-scale parameters** (batch size, frames, optimizer, logging, devices) live in an *experiment* profile, independent of task: `benchmarl/conf/experiment/base_experiment.yaml` is the framework default (small-ish); `fine_tuned/vmas/conf/config.yaml` is the "reproduce the published benchmark" profile (600 envs/worker, 60k frames/batch, 10M-frame budget, wandb). A real M1+ run should pick a profile at this level, not invent new fields — following the same task/experiment split BenchMARL and the published fine-tuned configs already use, and the Level 0/1/2 compute + wandb logging conventions from `coding_rules.md` rules 13–14.
- Selecting one of the six tasks on the CLI is exactly `task=vmas/dropout` / `vmas/give_way` / `vmas/passage` / `vmas/transport` / `vmas/wheel` / `vmas/buzz_wire` (matches the file names above); no code changes are needed to run any of them today.
